# AI画面升级执行规范

版本：2026-10-05 · v4  
维护位置：`D:/Codex/项目/画面质量规范/AI画面升级执行规范.md`  
适用范围：之后的游戏三维建模、关卡搭建、材质、灯光、场景视觉升级及其验收。  
依据：[Can It Code? — AI Built This Space Game From Scratch — Here's Exactly How](https://www.youtube.com/watch?v=Z9fyPTQVEdI) 的逐段画面与讲解研究，以及用户的 Blender、设计图、存储和版本保留要求。

这份文件是执行约束。开始适用任务前必须读取，并将当前项目资料、用户最近反馈和被否定的方案一起纳入判断。用户当前指令和具体项目约束优先；本文件不能成为擅自改题材、改玩法、增加审批、启用多代理或降低质量的理由。文中的流程细化、验收条件和模板是本次研究形成的工作规范，不冒充视频作者的原话。

## 1. 要交付的结果

目标是让真实游戏镜头中的画面具有明确的主角、可信的造型和材料、可读的空间、统一的风格及有变化的情绪。漂亮的孤立模型、复杂的节点、很多灯、很多面、很多零件，都不能替代这个结果。

必须同时通过三类检查：

| 检查 | 必须回答的问题 | 失败的含义 |
|---|---|---|
| 几何与功能 | 比例、接口、碰撞、通路、交互是否成立？ | 修结构或集成；不能靠光照掩盖 |
| 画面 | 玩家距离下的轮廓、材质、焦点、明暗是否达到本项目参考方向？ | 返回对应视觉阶段；脚本测试通过不等于画面通过 |
| 运行 | 在真实关卡、运动、状态切换及目标硬件上是否成立？ | 修完整场景；实验室截图不能替代 |

最终用户满意只能由用户实际评价确认。自检和参考对照用于提前发现问题，不得把“AI认为很好看”、评分、性能数字或完成数量写成用户已经满意。用户说最新一版差时，按既有回退规则恢复指定基线；不能继续以被否定的版本为默认方向。

## 2. 开始前必须形成的视觉设计

先检查已有资料，复用用户已认可的设计，不重复索要已有信息。缺少非关键参数时，按项目做出合理假设并记录；只有影响核心方向、无法从上下文推断的问题才需要询问。不得凭空增加“等用户批准设计图才继续”的停工要求。

建模前完成设计图与简短的视觉说明，至少明确：

1. **玩家的观看条件**：镜头类型、常用距离、视野范围、角色身高或尺度基准；哪些资产占据画面最多时间。
2. **主题与情绪**：地点用途、年代或制造逻辑、正常与剧情变化时的情绪。写成具体可见的目标，不能只有“高级、震撼、电影感”。
3. **参考与取舍**：少量一致的参考；每张说明取用的是轮廓、色彩、表面、光照还是构图。避免把互相冲突的参考全部叠加。
4. **形体语言**：大体块、次级结构、微细节；硬边与曲面的分配，模块尺寸、连接方式、英雄资产的主轮廓。
5. **材质与色彩规则**：主材质、粗糙度方向、现实尺度、颜色用途。重要交互还需形状、标记或运动提示，不能只依赖颜色。
6. **玩家视角与完整场地正交视图（用户要求，2026-10-04）**：任何场景与关卡设计都必须同时提供实际游玩视角，以及远距离的完整场地正交总览。正交总览至少包含高位斜向正交图与正交俯视图，完整显示场地外轮廓、建筑结构、通路、外围及背后区域，四周留白，不裁掉边界；有遮挡时补反向或侧向正交图。不能只交玩家初始位置效果图，也不能用广角透视或近景冒充正交图。构图说明焦点、前中后景与通路。概念效果图标明其性质，不能作为精确尺寸或已建成场景的证据；尺寸与连接关系另用可核对的正交结构图表达。
7. **灯光草图**：光源的物理位置与职责，谁照亮主角、谁引导动线、谁制造情绪。预先识别过暗、过曝和密集阴影风险。

在当前工程保存设计图和说明，并把它们与源文件关联。设计可以迭代，但必须先有设计再进入 Blender 制作。已有模型修改也先说明要保留什么、改变什么。

**多视角结构一致性（用户反馈，2026-10-05）**：正交图、白模图与玩家效果图必须对应同一设计，逐项保留主要部件数量、轮廓、厚度、折面、前后叠层、接口与空隙。不能为了绘图方便把多层复杂建筑简化成几个三角面，不能擅自添加原设计没有的大箱体。无法从参考看到的背面应明确标为补充设计。转白模只改变材质与照明，不删结构；生成图或手绘图无法证明一致时如实记录，后续用同一 Blender 源场景的不同相机验证。

**带材质的全场鸟瞰效果图（用户要求，2026-10-05）**：所有场景与关卡制作的效果图阶段，必须增加一张接近俯视的高位鸟瞰效果图，像从高处俯看完整场地一样，清楚显示主体、通路、地面点位及前后空间，同时保留立体结构、材质、厚度、折面与阴影层次。这张是用户用于判断整体设计的重要视图，不能只用简化白模、CAD平面或二维色块代替；它与玩家视角、严格正交总览及俯视结构图共同组成设计视图集合。完整入框、四周留白、多视角结构一致的要求继续有效。用户要求暂停某部分设计时，记录范围并停止在那部分增加方案；未做区域不冒称完成。

**场地边界与可达性**：按玩法设计连续外围遮挡与碰撞。训练场不能因只显示孤立地板而让玩家从无遮挡边缘跳落；开放天空和通透的围栏可保留空间感，不等于开放可逃逸边界。防翻越高度、踏脚面、门口与角落接缝须依据实际玩家运动核对，在引擎中测试跳跃、滑铲及连续移动后才能声称防越界通过。

### 色彩规则必须按项目生成

视频的浅色面板、深灰地面、橙色交互、蓝色屏幕、绿色温室是一套特定太空站配色，不能强加给所有游戏。借用的是“少量颜色 + 明确用途 + 全资产一致”的方法。

本项目应形成一张语义表：`角色 / 颜色 / 使用部位 / 禁止扩散的范围 / 备用非颜色提示`。区分材质颜色与情境灯光，例如救援标识的红色材质与紧急状态的红色照明不是同一条规则。执行时检查比例和分布；不能把每个模型均匀涂满全部颜色。

## 3. Blender 源文件与真实制作证据

所有游戏三维模型必须在 Blender 制作，并保留可以继续编辑的 `.blend` 源文件。可以在 Blender 内用 Python 提高效率，但必须形成实际 Blender 场景、对象和可编辑几何；不得在 Godot 或其他运行脚本直接生成可见网格，再称为 Blender 建模。

该规则也适用于此后制作的可见灰盒、树、道具、角色、外景主角与模块。游戏引擎的碰撞体、触发器和调试标记可按功能需要使用，不得拿它们冒充完成的美术资产。视频中早期 Godot 原语和最终下载行星的捷径，不能覆盖用户的 Blender 要求。

每次建模交付必须保存一张实际打开并使用最终 `.blend` 的 Blender 界面截图。截图要能辨认当前文件、关键模型和真实编辑界面；不能用渲染图、代码输出、拼接界面或旧文件截图代替。

源文件与导出资产建立清单：资产编号、`.blend` 路径、导出路径、尺寸、单位、原点、材质、版本和使用场景。导出后必须在目标引擎重新检查比例、法线、材质、背面、接缝、碰撞及真实光照。复杂 Blender 材质不能仅凭导出成功就认为在引擎中完整重现：必要时烘焙贴图或在引擎重建对应着色，并做对照验证。

## 4. 工作顺序：先证明一个场景，再扩大

### 阶段 A：保存可比较的基线

保存当前运行版本、关键问题和用户反馈。建立固定镜头集合：完整场地高位斜向正交总览、正交俯视、入口、主视觉、反向视角、最弱角落、重要交互近景、材料检查近景。小任务可合并镜头，但不能漏掉它实际影响的视角。场景与关卡在设计阶段、Blender 组装阶段及真实引擎交付阶段均保留完整场地正交图；引擎总览可使用独立检查相机，不改变实际游玩镜头。

记录镜头位置、朝向、投影类型、正交范围或透视视野、分辨率、灯光状态与曝光等实际可用参数。后续对比使用这些参数。截图若位置或设置发生变化，必须说明；不能把摄影角度变化当成资产质量提升。完整场地、门后通路或外围结构未显示清楚时，视图交付退回补齐。

### 阶段 B：设计与空间验证

按设计图在 Blender 建立可见空间和主要轮廓，先检查房间用途、尺寸、通路、视线、可达性和轮廓识别。用目标镜头测试，不要只看俯视平面图。先让形体和空间成立，再添加小零件。

### 阶段 C：做一个代表性质量样本

选择一间能够代表项目的房间或一小段关卡，加上一个会经常出现在镜头里的重要资产。完成其形体、材料、灯光和交互，形成可运行样本。先在这个样本里修掉主要观感问题，再复制模块和批量生产。

样本应包含项目实际需要的材料和观看距离。默认检查正常状态；有明确剧情或玩法需求时，再检查紧急、夜间等状态。不得机械要求每个项目都有太空站的全部预设。

### 阶段 D：逐层升级与受控比较

先改轮廓与比例，再改次级结构，再改材料，最后组织灯光、环境和必要后期。每次提出具体缺陷、原因假设、改动和验证方法。尽量只改变一个主要变量；记录受控条件，避免无法解释的“全都改了”。

已成立的部分要保护：改树叶不能丢树冠轮廓，改材质不能把金属读成水泥，改灯光不能挡住通路，优化阴影不能毁掉空间层次。跨阶段变化后回看固定镜头。

### 阶段 E：扩展、集成、验收

样本通过后才扩展到全关卡。每个新房间保留自身用途和识别点，不应成为相同模块随机排列的副本。完成真实路线、运动、交互、剧情状态和性能检查，随后再交付。

## 5. 每个制作任务都要有短合同

不把“把整个游戏做漂亮”当成一个制作步骤。按可验证的资产、模块或场景划分任务，每项写清：

```text
任务：
使用的设计图与参考：
当前具体缺陷 / 原因假设：
需要达到的画面表现：
必须保留、不得改动的内容：
尺度、模块网格、原点与连接规范：
Blender 源文件和引擎使用位置：
验证镜头与状态：
数值检查：
视觉检查：
运行与集成检查：
通过条件 / 退回条件：
```

完成后进行专门的审查阶段，先看画面再读制作解释，按合同接受或退回。没有独立审查者时，由自己切换到审查阶段并如实标注“自审”；不能假称独立代理审核。是否调用子代理另按用户授权和适用规则决定，本文件本身不授权自动派生代理。

连续修改仍无改观时，回到缺陷定位和参考方向，换原因假设或制作方法。不得因为已花很多时间、模型已生成、脚本无报错就宣布完成，也不得任意降低验收条件。

## 6. 造型：大轮廓优先，细节有用途

### 所有资产

- 先让外轮廓、比例和功能在玩家距离下可识别，再考虑微细节。重要物体至少检查正、侧、斜三个方向及实际游玩距离。
- 大形体、中等结构、小细节有层级。微细节不能平均铺满表面，也不能用密集机械零件遮住缺乏设计的大体块。
- 合理的转折、倒角和曲面要在当前镜头里产生有效轮廓或高光。仅给错误的方块家具加极小倒角不算完成造型升级。
- 保留必要的硬边；不要把墙、机柜、道具全部磨成相同的圆滑体。避免不必要的过密面数，检查平面是否仍然平整、转折是否出现错误阴影。
- 所有细节要解释功能或制造方式，例如检修盖、连接件、承重腿、管线转接、握持区、散热区。无法解释的重复装饰优先删减或重设计。

### 模块

先确定项目所需尺寸、单位、网格、连接端截面、接缝策略与原点位置，再做母模块。视频的 0.1 m 管道网格、2 m 墙板等是具体案例，不是所有项目的默认尺寸。

在真实组合场景检查墙角、门框、窗框、内外角、管道弯头与终端，测量连接间隙和重叠。容差必须按项目单位和资产大小约定；不能用肉眼“差不多”，也不能把浮点运算要求成没有容差的字符串相等。

原点、朝向、端部截面和编号必须稳定。一个模块改动后抽查其实际实例，避免只在孤立模型中成立。

### 有机物

树木、植被及生物先定物种或形态特征、整体剪影、重量分布与层次，再做枝叶和纹理。细化后回看原设计，检查树冠类型、枝干比例、疏密与变体差异。不同树不能只靠统一比例缩放区分。

植被在引擎中检查背面、透明排序、阴影与远距离形状；从路面看要有空间层次，不能挡住必要通路。是否使用透明、裁切或实体叶片，按实际引擎与项目条件选择并验证成本。

### 第一人称英雄资产与角色

先统一握持姿势、手部来源、工具原点和人物尺度，再分别制作；用组合预览证明手、工具和人物能够一起工作。不得让独立制作的手套与全身模型叠出两只手。

视频的 41 个刚性部分、17 个关节适用于其硬壳宇航服，不能推广为所有角色都不需要蒙皮。软组织角色按实际动作和形变需求设计。走路、转身、持物、受击和死亡都属于画面质量的一部分。

## 7. 材质：先识别材料，再谈分辨率

建立材料样本区，在中性检查光与实际场景光下都能辨认主材质。分别检查底色、金属属性、粗糙度、法线、纹理尺度、接缝和必要磨损；改变一个主要变量后锁定镜头比较。

粗糙度控制反射的清晰或扩散，是视频强调的关键。不能把金属全做镜面，也不能把所有物体统一调成粗糙灰色。材料之间应有可信差异，表面内部的变化要服从加工和使用方式。

纹理大小必须与真实物体尺寸相符。同一纹理放大后可能像混凝土，缩小后才像细腻涂层；不能仅提高贴图像素就宣称升级。对主要材料给出两到三个候选世界尺度，在同一镜头和灯光下比较并保留最合适者。

法线贴图主要改变表面受光，不会自动改变真正的轮廓；需要轮廓的结构应进入 Blender 几何。发光表面与照亮周围是不同效果，必须按项目 GI 或实际灯光方案验证。Godot 相关技术依据见 [StandardMaterial3D 官方文档](https://docs.godotengine.org/en/stable/tutorials/3d/standard_material_3d.html)。

程序纹理、拍摄纹理或其他贴图来源按目标选择；视频选择程序纹理是作者的制作选择，不是程序纹理必然优于扫描纹理。来源、许可、可编辑材料和引擎结果应可追溯，不借用旧交付包里的材质或许可证。

## 8. 灯光：每盏灯有职责，每个状态可游玩

灯光调整前明确主焦点和路线。安排照亮主体的主要光、建立轮廓与层次的辅助光、引导玩家的局部光，以及必要的情境变化；一盏光可以兼任，但必须解释它为什么存在。

检查：主角能否一眼被找到；入口、出口和关键交互是否可读；暗部是否仍有空间信息；亮部是否保留材料；暖冷分布是否服务情绪；前中后景是否分开；灯具自身与实际照明是否一致。

“更亮”“更多发光条”“更浓的雾”“更强泛光”不能单独作为升级方向。先调主体关系和材料可读性，再考虑必要后期。后期必须说明解决哪个缺陷；不得用泛光掩盖细节、用暗光掩盖模型或用雾代替完整空间。

按项目保存可复现的预设。每种预设记录实际参与的光组、曝光或环境设置、阴影策略和可读性检查；不要编造视频未公布的参数。视频面板有 Greybox、Day、Night、Maintenance、Alert、Emergency、Brownout、Blackout 八个按钮，但讲解明确展开的是其中七种，Alert 的独立行为不能靠猜。

剧情停电可以减少信息，但必须保留玩法所需路径或替代感知方式。闪烁、运动和状态切换要用连续画面验证，不能用单张截图声称动态效果已经成立。

## 9. 性能：先找成本，再保护画面

在目标分辨率、实际视角和目标硬件上记录性能条件与帧时间。把照明贡献与阴影成本分开测试，先比较“关闭阴影”而不是直接关闭所有灯。优先保留决定空间形状、接触和主角质感的阴影，减少贡献有限的灯的投影范围或阴影，并在正常游玩镜头回查画面。

阴影成本与光类型、范围、投影方式、遮挡物和更新情况有关。不能把“每盏灯永远重画整关卡”当成准确模型，也不能照搬视频作者约 30→50 FPS 的结果作为本项目承诺；Godot 有阴影缓存等行为，须以本项目测量为准。见 [Godot 灯光与阴影官方文档](https://docs.godotengine.org/en/stable/tutorials/3d/lights_and_shadows.html)。

如果预算不能支持既定设计，先调整光的职责、范围、模块或材料成本，再复核视觉目标。不得默默取消关键效果后宣称画面验收通过。

## 10. 动态与集成：静态好看不够

角色和生物先在简单试验场检查动作，再在真实关卡检查完整行为。每次测试明确接触面、步态、重心、转向、持物与镜头。

- 步行：脚底接触、滑步、抬脚、重心与转向；坡面和实际碰撞环境不能只靠平地测试替代。
- 多足或贴面生物：身体目标与腿部目标同步，逐腿停步查看落点；地板、墙面、天花板以及表面转换分别检查。
- 工具与交互：同一手部模型、握持、接触位置、动作、火花或烟雾、进度提示要共同成立。
- 完整状态：空闲、移动、攻击、受击、死亡、停电或剧情切换；死亡后仍悬空、穿墙、脚悬浮等属于未通过，不能只引用作者“够用了”接受缺陷。

固定路线的完整录像和针对问题的短连续片段必须实际打开检查。无报错、坐标到达目标和按键模拟通过，只证明对应数值或功能，不证明画面质量。

## 11. 审查问题与退回条件

审查时先不读制作说明，看固定镜头和连续片段，然后回答：

| 观察问题 | 出现以下情况必须退回 |
|---|---|
| 1. 一眼能看出主体和空间用途吗？ | 没有主次，房间只能靠字幕解释 |
| 2. 主轮廓达到本项目参考方向吗？ | 方块堆叠、形态被新细节破坏 |
| 3. 比例和制造逻辑可信吗？ | 家具、门、握持或承重明显不成立 |
| 4. 转折在真实距离有效吗？ | 倒角存在于参数里，画面仍无有效变化 |
| 5. 材料一眼可辨吗？ | 金属、涂层、塑料等只靠颜色区别或纹理尺度错误 |
| 6. 颜色有组织和用途吗？ | 每件物体乱用全部强调色，交互提示混乱 |
| 7. 明暗引导目光和路线吗？ | 主体埋在暗部，亮部洗白，通路消失 |
| 8. 有前中后景和合理空间层次吗？ | 平铺一层、全画面相同对比和密度 |
| 9. 模块接缝与功能细节成立吗？ | 浮空、穿插、端部不一致、随机装饰 |
| 10. 动作与完整状态成立吗？ | 脚离地、手重复、转向或死亡失真 |
| 11. 改动是否造成回退？ | 局部细化破坏整体形状、可读性或既有反馈 |
| 12. 性能在真实条件下可接受吗？ | 未记录条件，或只有孤立试验场的数字 |
| 13. 证据与最终文件一致吗？ | 旧截图、未打开的最终文件、导出未回查 |

写清每项实际结论与证据。功能通过但画面失败，应分别记为“功能通过 / 画面退回”，不得合并为整体通过。没有重大问题、与设计对照成立并完成运行检查后，才能标记为“自检通过、可供用户评价”；不得代替用户表示赞叹或认可。

正文说明做了什么、它改善什么、怎么验证、还有什么限制。不能只罗列术语、面数、贴图分辨率和已完成文件数。保留用户最近的明确反馈与被否定方向，作为下次开始时的资料。

## 15. 颜色搭配、组合与局部改色方法（2026-10-04补充）

本节由实际配色退回与公开颜色教学研究形成，属于执行方法。依据：[Adobe颜色关系与测试](https://www.adobe.com/uk/creativecloud/design/discover/color-wheel.html)、[Gurney限定色域](https://gurneyjourney.blogspot.com/2011/09/part-2-gamut-masking-method.html)、[暖冷配色对照](https://gurneyjourney.blogspot.com/2011/09/part-3-gamut-masking-method.html)、[颜色恒常性示范](https://gurneyjourney.blogspot.com/2010/01/color-constancy.html)。以下制作流程与退回门槛是项目方法，不是来源的原话或普适审美定律。

1. **先识别固定颜色，再设计变动颜色。** 局部升级先列出受保护的主色、暖冷方向、明暗与材料，新资产必须与它们同屏搭配。禁止只在新资产上选一套漂亮色块，再假设它一定适合原场景。
2. **分别组织色相、明度、饱和度与面积。** 同色相不保证统一，多色也不必然杂乱。用大面积主色、次级支撑色、中性过渡和少量强调色组织角色；记录颜色用在哪里，而非只列HEX。面积比例作为试验起点，不机械套用60/30/10。
3. **先做明暗分组。** 缩略图和灰度下应能分清主体、操作区与背景。背景局部的小亮点可能比平均亮度更抢眼；检查眼白、牙齿、反光和浅色衣服的密集分布。灰度只检查明暗，不代表完整的颜色验收。
4. **限定色域保留关系。** 选择少量可混合的颜色家族及中性灰，建立各自的明暗阶梯。允许皮肤、衣服、材料保留相对差异与冷暖变化。单色化仅在设计明确需要且完整场景验证成立时使用，不能作为默认“统一画风”按钮。
5. **给对比指定职责。** 邻近色可建立联系，互补关系可制造强调；并不保证成品协调。大面积高饱和对抗容易抢走主体。强调色的面积、明度和边缘锐度应与交互重要性匹配。
6. **在邻色中判断颜色。** 中性灰或低饱和色的冷暖感可能随周围颜色改变。材料固有色、环境色、光照色需区分；局部改色不能假设改变了整个场景光源。跨区域重复少量支撑色可以建立联系，但禁止越过用户锁定范围。
7. **颜色与材质分开试验。** 先控制色彩关系，另检查轮廓线、阴影层数、颗粒尺度、纹理方向与高光形状。统一材质语言不等于让所有材料都出现同样污损或金属反光。二维画面也必须保护形体和材质差别。
8. **输出配色关系图及同机位对照。** 至少包含固定色、主/辅/过渡/强调色及应用部位，成品缩略图、局部与原图。多候选应在关系与面积组织上不同；不得将五种整片着色当成五套完整配色设计。
9. **明确退回条件。** 新资产与原场景出现明显色温割裂；背景与操作区混成一片；高饱和或亮点密集竞争主体；颜色消除了材料识别；只有色块好看而实际场景失败；用户认为比原图更差。任何一项成立，都返回诊断，不以公式、HEX或自动评分宣布通过。

长期规则独立保存于本文件。具体游戏配色、失败案例与执行证据留在各项目的唯一美术owner及inspection，禁止反向把某款游戏的色调写成全项目强制配色。
