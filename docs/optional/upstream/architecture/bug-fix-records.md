# 错误与 Bug 修复记录架构

## 目的

为每次缺陷修复保留“问题是什么、先如何验证、根因是什么、改了什么、如何证明修好”的连续证据，避免修复规划混入产品架构或依赖聊天记录。

## 目录契约

每个 Bug 使用 `docs/错误与Bug修复日志/YYYY-MM-DD-任务名称/`，至少包含：

- `01-问题与规划.md`：用户现象、影响范围、修复前假设、先证据后改代码的顺序。
- `02-画线诊断.md`：修复前截图、画线图、测量值与已确认根因。
- `03-修复与验收.md`：代码改动、自动验证、人工手感待验项与交付版本。

图像和大体积证据放在对应应用的 `evidence/` 或 `D:/Codex`，日志只链接证据，不复制大文件。长期流程只由本文定义；任务目录记录当次事实，不反向修改架构原则。

## 必须遵守的修复顺序

1. 建立任务目录并写明现象与验收标准。
2. 捕获修复前证据；视觉或动作问题先制作带辅助线的对比图。
3. 由证据确认根因后才修改生产代码。
4. 使用同机位、同输入、同画线方法生成修复后证据。
5. 记录测试边界；自动验证不能代替用户的最终手感确认。
